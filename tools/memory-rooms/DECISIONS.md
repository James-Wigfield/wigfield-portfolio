Each entry: the decision, why, and how to change it. The build prompt
(`src/components/portal/modules/memory-rooms-plan/build-prompt.md`) is the spec;
these are the calls it left open.

## scene.json v1

6. **`rotY` convention: at 0 an object's front faces south (+z)**; 90 east, 180 north, 270 west (the three.js / Blender sense of rotation about up). The prompt's example had a desk on the north wall at `rotY: 180`, which under this rule faces the wall; the shipped example uses `rotY: 0`. *Why:* one fixed rule makes check-scene, the kit and the scorer agree. *Change:* only by rewriting every kit piece; don't.
7. **Camera `fov` is across the photo's long edge**, plus an optional `aspect` (width / height, default 0.75 portrait) and `roll`. *Why:* phones are held both ways, and "long edge" stays the same number (≈ 69–72° for a main camera) either way. three.js gets the vertical fov from `geometry.verticalFov()`.
8. **Schema additions beyond the prompt** (all optional): `notes`, `hero` view, object `label` / `mount` / `overlaps` / `params` / `accentMaterial` / `photos`, opening `color` / `open`, wall `thickness` / `skirting`, `style.exposure`, light `look` / `size` / `azimuth` / `object` and types `ceiling`, `spot`, `area`, `window`, `frame.y` (upper floors). Materials add stone, marble, velvet, chrome, brass, ceramic, plastic, paper, emissive; ground finishes add concrete, gravel, dirt. *Why:* each one removes a reason to write a bespoke script or to fail the 2 cm checks on purpose (`overlaps` for a chair under a desk, `mount` for wall-hung things).
9. **One validator, hand-written**: `validate.js` interprets exactly the JSON Schema keywords the schema uses and throws on any other keyword, and `scene_io.py` mirrors it line for line. *Why:* Ajv compiles validators with `new Function`, which Cloudflare Workers forbid, and Python needed the same rules without pip installs inside Blender.
10. **Walls are built outside the interior box** (`walls.thickness`, default 0.12 m), so `width`/`depth` are always the inside measurements you'd take with a tape.

## Storage and API

11. **Media row ids are derived from (spot, type, name)** (a v5-style uuid), and `memory_media` has two extra columns, `name` and `content_type`; `memory_spots` has `loc_source` ('gps' | 'pin' | 'typed'). *Why:* re-uploading photo 3 or a new render overwrites the same row instead of piling up duplicates, which makes every upload safely retryable from the outbox.
12. **`POST /spots` is an upsert that only refreshes the capture fields** and never resets `status`, `scene` or `sceneVersion`, so a late retry from a phone can't undo modelling work.
13. **Signed file links**: HMAC-SHA256 over `<r2Key>.<exp>`, `exp` rounded to 6-hour windows (12–18 h validity). *Why:* the URL stays identical within a window, so browsers cache photos and GLBs. The key is `MEMORIES_SIGNING_KEY`, or derived from the passwords when unset (changing a password then expires every link, which is fine).
14. **`MEMORIES_ROW_STORE` is `"supabase"` in `wrangler.jsonc` vars and `"local"` in `.dev.vars`** (which overrides vars in `wrangler dev`). Production therefore fails closed with a clear 503 until the SQL has been run, rather than silently writing JSON rows into R2.
15. **The R2 binding is in `wrangler.jsonc` now**, which means the next `npm run deploy` (of anything) fails until the bucket exists: `npx wrangler r2 bucket create memory-rooms`. It's on the deploy checklist.
16. **Uploads stream straight into R2** when the request has a content length (a 100 MB scan never sits in Worker memory). Limits: photo 15 MB, thumb 2 MB, scan 100 MB, model 40 MB, render/compare 25 MB.
17. **The Supabase row store has not run against the real database** (the SQL wasn't run, per the rules). Both stores pass `tools/memory-rooms/api-check.mjs` (31/31): the local store directly, and the Supabase store against `tools/memory-rooms/pgrest-stub.mjs`, an in-memory PostgREST stand-in that enforces the SQL's checks, foreign key and unique keys; the rows it stored have exactly the SQL's columns. *Do:* after running the SQL, set `MEMORIES_ROW_STORE=supabase` in `.dev.vars` and run `api-check.mjs` once against the real project.

## Map

18. **The atlas also draws Mexico, faintly, north of 24°N**, so the border near San Diego and the Gulf doesn't end in the void. Canada is clipped south of 60.5°N (BC and Alberta's northern border is 60°N). 196 KB, 40% of the source points kept. *Change:* `tools/memory-rooms/build-atlas.mjs`, then re-run it.
19. **Typed places come from an offline gazetteer** of trip places (plus raw `lat, lng`), not a geocoding service. *Why:* works with no signal, no API key, no third-party calls from the phone.

## Render workflow

20. **Wrappers**: `build.mjs` = check-scene → build_room.py → compare (one compare round), `bake.mjs` = bake_export.py. The individual scripts still exist and are what the wrappers call.
21. **`compare.png` has four columns per photo: photo | render | 50/50 overlay | edges** (photo edges red, render edges blue, matching edges dark), and three scores per camera (structure = edge-map correlation, tone, colour). *Why:* misaligned cameras are obvious in the overlay, the self-test's modeller found 2–5 cm offsets only by comparing edges (so that column was added after the run), and the scores show whether a round helped. They're guides, not grades.
22. **check-scene's float rule**: a thing is held up if its base is on the floor, on another object's top under its centre, against a wall/object side (wall-mountable kits or `mount: "wall"`), or its top touches the ceiling. `mount: "free"` opts out. Door swings are a warning, not an error.
23. **Baked textures are display-referred**: the bake goes through AgX (the same view transform as the Cycles stills) before it is saved, so the viewer draws them with no tone mapping and matches the renders.

## Blender pipeline and kit

24. **Every interior piece is real geometry, built in local space inside its size box** (checked to 1 cm by `kit/preview.py`); duvets and curtains run a short cloth simulation and fall back to a procedural drape if it misbehaves. Piece options are in `kit/README.md` (e.g. bunk `ladder`, sofa `seats`/`arms`, shelf `books`). The bed's `accent` is its frame and headboard (a fabric accent gives an upholstered bed).
25. **Walls are mitred at the corners and their cut tops are a flat dark colour**, like an architectural section, so the dollhouse cut reads clearly.
26. **Look: Cycles + AgX "Medium High Contrast", auto exposure per `style.mood`.** One look for every spot. *Change:* `lighting.py` / `common.py`.
27. **The bake captures all lighting (not diffuse only)** so metals keep their colour, and furniture faces within 6 cm of a wall are baked a second time with the walls hidden, so the back of a bookcase against a cut-away wall isn't black.
28. **Up to 4 atlases per room** (2048 px each) when one would fall below ~110 texels/m; materials are `baked_atlas0..3` with `KHR_materials_unlit`; each object is one joined mesh `obj__<id>__mesh`; each wall one `wall_<side>` mesh including its glass and door. Bedroom: 2.1 MB, 1 atlas; diner: 2.1 MB, 4 atlases.
29. **The three-quarter/hero camera picks the corner whose cut-away walls have the fewest tall or wall-hung pieces against them.**
30. **Exterior photo-camera renders get a ground that runs to the horizon** (only in the stills, never baked), so they compare fairly against real photos.
31. **Baking is the slow step** (~2–2.5 min per room at 256 samples; build + 64-sample renders ~10–15 s). Blender bakes can't sample adaptively. *Change:* `bake.mjs --samples 128` halves it at some noise cost.

## Front end

32. **The 3D pages (spot, group) load on demand behind an error boundary**, so the map and capture flow (often on a weak signal) never download three.js and can't be broken by a viewer error. Spark (2.8 MB) loads only when Scan is chosen.
33. **The capture draft is saved to IndexedDB as you go** (stores `draft`, `draftPhotos`), so iOS dropping the tab loses nothing; Save moves it to the outbox (`outbox` + `outboxFiles`) in one transaction. Retries back off 5 s → 5 min; a 401 pauses the queue and shows the gate; files rejected for good (400/413/415) wait for a manual Retry; sent entries are pruned after 24 h, unsent ones never.
34. **A service worker (`public/memories-sw.js`, scope `/memories`, production builds only)** caches the app shell so `/memories/new` opens with no signal once the site has been visited. It never caches `/api/`.
35. **Save is allowed without a location** (the spot shows under "No location"); typed places store the place's rough radius as `locAccuracyM`.
36. **The who-picker appears only on the map and capture pages**; spot and group pages don't need it.
37. **The viewer stays mounted between spots** (one WebGL context per visit); panning is off (orbit + zoom only); arriving at a photo viewpoint shows the photo fully, and you slide towards the model.
38. **Pins and viewpoints are off in Scan mode**, because a Scaniverse scan has its own coordinates. Scans are flipped 180° about x by one constant (`SCAN_CORRECTION`); only Spark's public sample `.spz` has been tested, not a real room scan.
39. **Status reads by shape, not colour** (captured = ring, modelling = half, rendered = filled) on the map and in every status dot, so the palette keeps one accent (terracotta) for selection and emphasis, plus red for errors only. (From the screenshot review.)

## From the self-test

40. **"North" = the wall you face standing in the main doorway.** The capture shot guide's back-left / back-right / front-right / front-left corners are then NW / NE / SE / SW, the order photos 1–4 arrive in. *Why:* the self-test's modeller found "the wall the first photo looks at" ambiguous (a corner photo sees two walls).
41. **check-scene allows a camera standing in a doorway** (up to 0.6 m outside the wall line, within a door or opening's span), as a warning: "wide from the door" photos are taken there.
42. **Skirting takes the first WINDOW's colour (else off-white)**, never a door's. Before, whichever opening was listed first with a colour won, so a painted door made teal skirting.
43. **The self-test truth closes its door** and photo 6 stands just inside it: with the door half open, the camera in the doorway saw only the door leaf.
44. **The self-test is honest about its advantage**: the photos come from the same kit and renderer the modeller uses, so expect larger errors on real phone photos (see the README's worked example).
45. **In dollhouse view only wall-HUNG things hide with their wall** (`mount: "wall"`, or a frame/curtain/tv/sign/shelf flush with the wall and off the floor; curtains even when floor-length). A bookcase or TV unit standing on the floor against a hidden wall stays, because hiding it only reveals the dark floor it shaded in the bake.
46. **Bake fixes after the self-test**: each door gets a `wall_<side>__threshold` that hides with its wall, the band under walls is always the flat section colour, and the furniture-only second bake pass now has 6 px island gaps and no margin bleed, so it no longer paints a tan band along the wall/ceiling line.

## The Mapbox world map (2026-11-18)

47. **Both maps (the `/memories` map and the capture pick map) are Mapbox GL JS globes**, with the SVG atlas kept as the fallback. `map/SpotsMap.jsx` and `map/PickMap.jsx` choose: Mapbox when `VITE_MAPBOX_TOKEN` is set, WebGL 2 works and the browser is online, else the atlas (`AtlasSpotsMap.jsx`, `AtlasPickMap.jsx`). A Mapbox map that fails at runtime (style or token error, no load within 12 s, or 8 s for the pick map, lost GPU, or losing signal mid-capture) swaps to the atlas in place. Overrides: `?map=atlas|mapbox` or localStorage `mr:map`.
48. **One map load per page.** Every `new mapboxgl.Map()` is billed (5,000 a month on the no-card trial). `mapbox/useMapbox.js` makes the map once per mount and nothing else creates one. Spots, clusters, cards, labels and the pin are an SVG overlay redrawn from `map.project()` on every camera move (via `useSyncExternalStore`, so it paints in the same frame). StrictMode's double mount is safe because the module import is async and the first cleanup cancels it. page-check asserts `window.__mrMapLoads === 1` after filters, clusters, cards and zooms.
49. **Clustering stays screen-space (`clusters.js`), not Mapbox's own.** Mapbox clusters are WebGL symbols: they can't use the CSS status glyphs, they have no focus or aria, their members come back from an async query, and they regroup only per integer zoom. `clusters.js` on projected points keeps the markers as real buttons, the "rooms of one building never split" list, the card anchoring and the label avoidance identical on both engines, and it's plenty fast for a trip's few hundred spots. Points on the far side of the globe are dropped by a project → unproject round trip.
50. **The globe opens on the trip.** The home view fits the spots inside the trip area (the old `ON_MAP` box), capped at zoom 6, or the whole trip area (`FIT_EXTENT`) when there are none. Spots elsewhere (Perth) are on the globe too; "n elsewhere" turns the globe to them as well as scrolling the list. The reset button reads "Back to the trip".
51. **Style = the Mapbox tokens in `memory-rooms.css`.** `mapbox/style.js` repaints Mapbox Light layer by layer from `--mr-map-*` (new: `park`, `building`, `road`, `road-major`, `label-strong`, `space`, `glow`), light and dark, with mono uppercase country and state names, no POIs, and quiet subways. Colours go through the browser first because the built CSS minifies `rgba()` to `#rrggbbaa`, which Mapbox can't parse. Candidate B, Mapbox Standard tinted through its config, is behind `?mapstyle=standard`; `tools/memory-rooms/dev/map-style-shots.mjs` renders both side by side.
52. **The trip's place labels (`PlaceLabels.jsx`, shared by both engines) show between "about 28° of longitude in view" and zoom 7.5**; below 7.5 the base map's town labels stay hidden, so the two never double up. The pick map shows the base map's labels at every zoom, since that's where you find your street.
53. **On the pick map a tap also zooms in four levels around the pin, up to zoom 15.** The atlas stopped at town level, so one zoom-in on the first pin was enough; a street-level map needs tap, tap, tap. Dragging the pin never moves the map. A GPS fix flies to zoom 16, and a typed place to its radius.
54. **`mapbox-gl` is pinned to 3.34.2** (15 days old at install; 3.35.0 was 5 days old) and is imported dynamically together with its CSS, so it's a separate 524 KB gzipped chunk that only the `/memories` maps fetch.

## Rendered spots on the map: markers, then live 3D (2026-11-18)

Brief: `Documents/memory-rooms/prompt-dumping/map-3d-renders.md`. Phase 1 (markers) was shown before phase 2 (3D) started; James said go on the three calls flagged then (55 engine, 59 map.glb, 61 tilt).

55. **A rendered spot stands on the map as its hero cut-out**, not a status dot: `render/marker` (`renders/marker.png`, the hero trimmed to its content and shrunk to fit 240 px, a 12–24 KB palette PNG instead of a 4.5 MB hero). The image's bottom centre sits on the location over a soft contact shadow (an SVG radial gradient, `--mr-marker-shadow`); a ring on the ground marks the selected or focused one. Long edge 44 → 124 px between zoom 3 and 13 (36 → 100 on a phone): a diorama with a screen size, since true scale is invisible. *Why PNG, not WebP:* `push.mjs` already uploads every `renders/*.png` as a render row, so it needed no API change. *Why feathered edges:* the Mazda hero is full-bleed (the camera cropped its ground plate), which made a hard rectangle. A spot without a marker shrinks its hero in the browser, once per page session, one hero at a time (`map/markerImages.js`); the atlas draws the same markers.
56. **Clusters keep the numbered disc and fan up to 3 of their rendered spots' markers behind it** (70 % of the marker size, ±15°). *Why:* it says "there's a finished room in here" before you zoom, without changing what the disc does; it's decoration, so the number stays the button.
57. **Painter's order, and dots on top.** Markers (and 3D models) are drawn top of screen first, so the lower one is in front; plain status dots and clusters are a layer above them, so a captured spot is never hidden behind a marker. The overlay is above the map canvas, so a marker that a 3D model stands in front of would cover the model: that marker shows as its dot instead.
58. **Phase 2 engine: one three.js custom layer in Mapbox's own WebGL context** (`map/mapbox/models3d.js`, a lazy 12 KB chunk + the shared three chunk), not Mapbox's native `model` layer. The native layer can't hide the walls facing the camera as the map turns (no per-node visibility), so no dollhouse; it lights models (the bake is the light); it's true scale in metres; it keeps the full 2048 px atlases; and its GLB url would be a signed link that expires in the style. The custom layer reuses `viewer/bakedMaterials.js`, `dollhouse.js` and `dispose.js` as they are.
59. **Fixed screen size by giving each diorama its own camera and square**: a perspective camera (the hero's 34° fov) fitted to the model's bounding sphere, drawn into a viewport + scissor square positioned so the footprint centre lands exactly on `map.project(location)`; depth is cleared inside that square only. *Why:* placement through `map.project()` means the globe → mercator transition needs no special case (custom layers get globe matrices below zoom ~6; at 15+ it's mercator anyway), and models never meet the map's depth. Squares are drawn top of screen first.
60. **North up shows the hero's side.** The room is turned so that, with the map facing north, its diorama is seen from the hero render's corner (`scene/heroView.js`, a port of `build_room.py` `choose_interior_corner` / `choose_exterior_azimuth` + `lighting.py`'s sun; it matches Blender on all 7 local spots, azimuth and elevation, including 3 with `scene.hero`), and at the map's rest tilt (52°) it shows the hero's elevation. So marker → model keeps the same view. It turns with the bearing and tilts with the pitch (view elevation = hero + 52° − pitch, kept within 22–72°). This turn is a display choice: a room's north is the wall you face from its doorway (40), no bearing is stored, and nothing presents it as the real orientation.
61. **`model/map` = `map.glb` (a contract change, CONTRACTS.md §2 + §4)**: room.glb with textures shrunk to 512 px WebP and the geometry quantised + meshopt-compressed (glTF-Transform `meshopt()`), node and material names checked unchanged. *Why not just shrink textures in the browser:* the GLBs here are mostly GEOMETRY (0.7–2.9 MB vs 0.3–1.1 MB of WebP), so a phone would still download 1–4 MB per room; map.glb is 300 KB–1 MB (≈ 3.5×; gzip would halve it again, not done). The Worker's model `:n` is now `room` (any other name, as before) or `map`; the viewer asks for `room` by name (`lib/spots.js roomModelOf`), since `map` sorts first. A spot without map.glb loads room.glb and its atlases are shrunk to 512 px on a canvas before they reach the GPU. New devDependencies (pinned, > 2 weeks old): `@gltf-transform/core|extensions|functions` 4.5.1, `meshoptimizer` 1.3.0; an npm `overrides` entry makes glTF-Transform's `ndarray-pixels` use the project's sharp 0.34.5 (its own 0.35.5 loaded a second libvips into the same process and every sharp call failed with "colourspace: parameter space not set").
62. **When and how many**: models appear at zoom 15 and go below 14.6 (no flicker at 15); only spots standing alone (not in a cluster), on screen with a half-diorama margin, nearest the centre first, at most 3 on a phone and 6 wide; loaded one at a time, nearest first; anything that leaves the list is disposed at once (geometries, materials, textures, ImageBitmaps). The layer outlives an empty list (nothing is drawn) and goes with the map. A load or draw failure puts that spot (or, for a draw error, every spot) back to its marker for the page's life.
63. **Tilt and rotation**: the map stays flat and north up below the threshold. Past it, rotation and tilt unlock (up to 60°; right-drag does both, two fingers on a phone) and a flat map eases to 52°; zooming back out eases it flat and north up and locks both again. Nothing is changed mid-gesture (it waits for `moveend`). A compass button ("Turn north up") shows while the map is turned. "Back to the trip" flies flat and north up. The overlay maths was already `map.project()` / `unproject()`, which handle pitch and bearing.
64. **The spots map's Mapbox canvas has MSAA on** (`antialias: true`, a constructor option, not another load); the pick map stays off. The dioramas share that canvas and were visibly jagged without it.
65. **Markers, 3D models and fanned clusters let the pointer through** (`data-pass`, `pointer-events: none`): a 100–270 px button swallowed every drag that started on it, which on a phone is most of the map. A click or tap on them is found from Mapbox's own `click` event (it only fires when the pointer didn't drag) by hit-testing the same boxes, top layer and lowest on screen first; hover sets the pointer cursor and the marker lift. The keyboard and screen readers still use the overlay buttons (role, focus, aria, `data-mr` hooks unchanged); a 3D model's selection/focus ring is drawn on the ground in 3D. Small dots and cluster discs keep their own hit circles, as before.
66. **Live spots haven't been backfilled, and the order matters: deploy first.** `backfill-map-assets.mjs` makes `render/marker` and `model/map` from the stored hero / room.glb and refuses any non-local Worker without `--live`. A Worker from before this change stores every model name as room.glb, so `map.glb` sent to it would overwrite the real room (which the viewer can't decode: no meshopt decoder there): the Worker's ping now lists `models: ["room", "map"]`, and `push.mjs` and the backfill skip / refuse `map.glb` without it. Once deployed and backfilled, the 4 live rendered spots get small markers and map.glb; until then they fall back to the hero shrunk in the browser and room.glb (heavier, same look).

## Editing a spot after capture (2026-11-18)

67. **Editing is its own page, `/memories/:id/edit`** (`pages/EditPage.jsx` + `pages/edit/`), reached from an "Edit" link on the spot page's panel, not a sheet over it: the phone's back button works, and the spot page's 3D viewer never runs alongside a map. Editable: name, note, the place (pin / GPS / typed place / coordinates, and the place name), the captured day (the time of day stays, in the phone's time zone, as the spot page shows it) and who saved it; kind and size only while the spot has no scene (after that they show as fixed, with one line saying the 3D room was built from them). Photos, status, scene and frameGroup belong to the render pipeline and aren't editable. No delete UI (the API's soft delete stays script-only).
68. **One location picker for capture and edit** (`capture/LocationPicker.jsx`). StepLocation is now its title plus the picker, with the same DOM, so capture's page-check walk passes untouched. The picker takes `{ loc, onChange(prev => next) }`: an updater, because a GPS fix lands seconds later and must label itself from the location as it is then. The edit page also passes `anchor` (where the spot was saved). The spot's saved place name then stays while the pin moves a little, and switches to the nearest gazetteer place once the pin is more than 25 km from the anchor, unless it was retyped in this edit. A line says so ("More than 25 km from San Diego, CA, so the place now reads Perth, WA"). With no gazetteer place within 60 km, the name is cleared rather than left wrong, and the line says that too. Capture never sets those fields, so it labels exactly as before.
69. **The picker's map mounts only on "Change location"**, never with the page: a title fix costs 0 Mapbox loads, a location fix 1. Once open it stays open (reopening would be a second load). It opens on the saved location at street zoom (16).
70. **A POST for an existing spot id now changes nothing** (CONTRACTS §3, was "refresh the capture fields"). *Why:* the outbox re-POSTs a capture whenever its first POST's answer was lost (or a media PUT 404s). Before, a late retry — e.g. phone A's capture landing hours later, after Justin fixed the place on phone B — would have put the capture-time values back over the edit. The outbox entry is frozen, so a legitimate retry always carried identical values anyway. `seed-dev.mjs` now PATCHes the demo values after its POST, so re-seeding still resets them.
71. **PATCH learned `locSource`, `capturedAt` (ISO 8601 with a zone and a real calendar day; `Date.parse` alone accepts "1") and `createdBy`.** lat/lng go through the same `latLng()` check as the POST (both numbers in range, or both null; a PATCH must send both), it refuses a kind change while the spot has a scene, and every `details` entry starts with its field name so the form puts it next to that field. Still no new columns: `loc_source`, `captured_at` and `created_by` already existed.
72. **Two phones: `ifUpdatedAt`.** The edit form sends the spot's `updatedAt` from when it opened; if the spot changed since, the Worker answers 409 and saves nothing. The PATCH response re-reads the row, so its `updatedAt` is the Supabase trigger's value and works as the next `ifUpdatedAt`. On a 409 the page fetches the spot. If only the render side moved (status, scene, photos), it rebases and saves once more by itself. If the details moved, it says "Justin changed this spot while you were editing" and offers Reload, which brings their changes in under the fields you changed. The name is inferred as the other person from this phone's who-picker: no column records who edited, so a script's change would be attributed to the other person (but scripts only touch the render side, which never shows the line). Scripts send no `ifUpdatedAt`, so they're unaffected. The check is read-then-write, not atomic: two saves in the same ~100 ms could both pass (accepted for two people).
73. **Edits never go through the outbox.** Offline, Save is disabled with one line saying why. What's typed is kept per spot in sessionStorage (`mr:edit:<id>`, with the spot as the form opened, so the page reopens offline from it) until it's saved or discarded. Queueing edits would mean replaying them against a spot that may have changed since: the conflicts aren't worth it for a fix that can wait for signal.
74. **Leaving with unsaved changes asks first on the page's Back (an inline "Leave without saving?", no dialog) and on reload/close (beforeunload).** The phone's back gesture and the header links can't be intercepted with a non-data router (no `useBlocker` with `<BrowserRouter>`), but the draft survives them: coming back says "Picked up where you left off". After a save the page goes back through history when it came from the spot page (so back from the spot page still reaches the map), and the spot page shows "Saved. The changes are live." once (`lib/flash.js`, in memory).
75. **No edit history.** The old location is gone once a new one is saved. Keeping the original capture location (a `capture_loc` column) would protect a GPS fix from a careless drag, but the edit page shows the saved location until Save, and "Put the saved location back" undoes a move before saving. *Change:* a nullable jsonb column + a CONTRACTS change, written once on the first location edit.
76. **The Mapbox pick map's overlay `<svg>` is `touch-action: none`** (`.mr-pickmap .mr-mapoverlay`). Chrome ignores `touch-action` on an SVG `<g>`, so on a phone a finger dragging the pin scrolled the page instead (pointercancel after two moves) whenever the step scrolled. That was true in capture as well (it only showed now: page-check had only tapped). The overlay is `pointer-events: none` apart from the pin, so the map's own gestures are untouched. The atlas pick map was already fine (its `<svg>` root had it).

### "See it in your space" (AR)

77. **One entry, three paths, by what the device can do** (`ar/ArEntry.jsx`, its own lazy chunk; `ar/support.js`). iPhone / iPad → AR Quick Look (detected as Apple documents it, an `<a>` whose `relList` supports `ar`, with the UA as the fallback for in-app browsers and the headless check); Android Chrome → WebXR `immersive-ar` (`navigator.xr.isSessionSupported`); a desktop → a QR code; a phone with neither → one line. It shows on every spot whose stage is a baked GLB, under "Walk in".
78. **The iPhone file is made in the browser, not by the pipeline** (`ar/usdz.js`): three's `USDZExporter` over a clone of the room the viewer already loaded (shared geometry and images, nothing re-downloaded). Each surface goes out as a `MeshStandardMaterial` with a **black base colour, roughness 1, metallic 0 and the bake as its emissive texture**: Quick Look lights every material, but adds emission after its lighting, so the baked look shows instead of being relit. Atlases go out as JPEG (bakes have no alpha), capped at 1024 px (tabletop) / 2048 px (life). Tabletop = 1:20 without the `ceiling` nodes (a static dollhouse: Quick Look can't hide walls as you walk round); life = 1:1 with everything. Geometry below y = 0 (a floor slab's underside, the diner's 0.4 m ground skirt) is clamped to 0 in a copy, because Quick Look rests the model's lowest point on the surface. Cached per spot + GLB (`r2Key|bytes|createdAt`) + `sceneVersion`, in memory and in Cache Storage (`mr-usdz-v1`). *Why not the bake-time `model/usdz` fallback:* the browser files pass `usdchecker --arkit` on all 8 local rooms, need no backfill of the live spots and no Worker change. *Size:* 4.5–11.5 MB; the exporter writes geometry as text (the warehouse's tabletop is the biggest), but the file is made on the phone from what it already holds, so nothing extra is downloaded.
79. **WebXR runs inside the existing viewer** (`ar/xr.js`, `RoomViewer.enterXR/exitXR`): the same renderer, room and baked materials; the viewer stops its own frames while the session's loop draws. A reticle follows a hit test from the screen centre; a tap places the room (floor on the surface, turned so you face the side the spot page opens on); then one finger drags (a transient-input hit test), two fingers pinch (1:100–1:1) and twist (DOM overlay touches). Tabletop runs `dollhouse.js` every frame from the phone's position; life size shows everything while you stand inside the footprint and opens the walls facing you from outside it. The loop is set before `setSession` and only runs on XR frames, after setup (set after, three also ran it from the window's rAF). `xr.js` is fetched as soon as the panel opens, so `requestSession` still runs inside the tap's user activation on a slow line; a setup that fails part-way ends the session and puts the viewer back.
80. **The desktop QR code** (`ar/qr.js`, `qrcode-generator` 2.0.4 pinned, lazy) opens `/memories/<id>?ar=1`, which opens the panel on the phone. Always dark on light (`--mr-qr-ink` / `--mr-qr-paper`, both themes) with the 4-module quiet zone the QR spec asks for, since the page around it can be dark.
81. **`usdchecker --arkit` = `tools/memory-rooms/usdchecker.py`**: the `usd-core` wheel ships no command-line tools and 26.x dropped the compliance checker, so it runs `UsdUtils.ComplianceChecker(arkit=True)` on usd-core **25.8**, and fetches the usdShaders resources (`shaderDefs.usda` + 4 glslfx, public) the wheel leaves out, without which the shader rule crashes.

### "Play the trip" (the flyover)

82. **A state machine plus one camera driver per map** (`map/flyover/useFlyover.js`; `mapbox/useFlyoverMapbox.js`; `flyover/useFlyoverAtlas.js`). The route is a GeoJSON line source + layer (`mr-route`) on the page's ONE map, under the 3D layer: `__mrMapLoads` stays 1. Great-circle arcs (`flyover/plan.js`), drawn as the camera flies.
83. **Stops = spots with a location, oldest capture first** (ties: created, then id), through the page's filters. The brief said "who / kind"; the page's filters are who and **status** (there's no kind filter), so those apply and none was added.
84. **The camera**: rendered stops dive to zoom 16.2 at 55° (past MODEL_ZOOM, so the existing 3D layer stands the diorama up, within its cap, and disposes it on the way out) and orbit 36° over the 4 s linger; captured-only stops stop flat at zoom 12.5 with their first photo in the caption. Hops over 1,500 km pull out to zoom 1.6 on the way (`flyTo` `minZoom`): WA → the USA crosses the globe. 3.2 s a flight (6.5 s long), halved at 2×. It ends on the whole route, flat, the short way round in longitude (so it can cross the antimeridian). *When it can't:* stops more than ~150° of longitude apart can't share one view of a globe (Perth and New York are nearly antipodal: one is always past the horizon; a flat Natural Earth end view was tried and only drew half the world on this map), so the end view fits the main region, the largest group of stops split at 60° gaps, and the route runs over the horizon to the rest.
85. **While it runs, the flyover owns the camera**: the tilt rule (`useTilt`) and the follow-the-trip view are held, a drag or pinch pauses it, and exit puts back centre, zoom, bearing, pitch, padding, the tilt limit and the selected card, and removes the route. On a phone the map takes the whole screen for it (the list comes back on exit) so the bar sits under the thumb; the caption and bar keep 26 px clear of the Mapbox logo and attribution (their terms).
86. **Reduced motion: cuts, not flights** (a 220 ms fade to the page colour, a jump, a fade back; no orbit). **The atlas** gets the simpler version: pan/zoom to each stop (k = 6), the route as an SVG path clipped to what the atlas draws; a stop off the atlas (Perth) shows its caption over the trip. `?play=1` starts it at load (it waits for the spots) and drops itself from the URL on exit.

### Walk in together

87. **`/memories/:id/walk`, its own lazy chunk** (`pages/WalkPage.jsx`, `walk/`), from a "Walk in" button on every spot with a GLB, which also shows who's in the room now (the DO's presence, asked every 15 s while visible). You're the person picked at the gate. One WebGL context (the page has no viewer), the full room.glb, everything disposed on leave.
88. **Characters: PixelLab, two generic travellers** (blue and orange jackets; no likenesses), standard mode, 8 directions at 64 px. Walk in 5 directions (the other 3 mirrored), idle = the 8 rotations, wave / sit / jump facing the camera only (emotes face the viewer). A's jump frame 1 was drawn from the back and is dropped. 17 of the 19 daily generations, nothing bought. `tools/memory-rooms/build-characters.mjs` packs an export into one sheet + layout (feet on one row per animation); `walk/characters.js` is the one file to change to swap a character.
89. **Where you can walk comes from the GLB** (`walk/grid.js`): every triangle with any part 0.15–1.7 m above the floor blocks the 5 cm cells under it (the band is clipped out, its outline traced so a thin wall blocks, its inside filled so a table top does); cells within 0.2 m of a blocked one are out; only the region reachable from the start (the first photo camera, else the centre) counts, so an octagon's corners stay walled off. Interiors are cut to the shell's box, exteriors to the `ground` plate. 20–65 ms on all 8 local rooms. Moving slides (axis-separated substeps); tap-to-walk is A* (8 neighbours, no corner cutting) straightened by line of sight.
90. **The view never gets blocked**: third person behind and above (3.6 m; wheel / pinch 1.3–9 m), the walls between camera and you fade (`dollhouse.js` with you as the centre) and the ceiling hides; furniture between camera and you hides too (a segment against each object's box: the shed's loft). The camera swings in behind you as you walk unless you looked round in the last 1.6 s. *Keys:* WASD (A/D step sideways), ↑/↓ walk, **←/→ turn** (so the keyboard alone can look round), Shift runs, E sits / stands / looks, 1–3 emotes, V first person, a click locks the pointer.
91. **Photo marks**: a ring where each scene camera stood (or the nearest walkable spot, for a camera held over furniture). Stand still on one for 0.35 s and the view flies to that exact camera and the real photo fades in over a letterboxed view, as in the spot viewer (re-implemented, not imported: the viewer is a different class); moving brings you back. The mark you start on waits until you've stepped off it.
92. **Seats**: chair, stool, armchair, sofa, bed and bunk objects within 1 m. You sit just in front of the seat (the sprite's seated pose over its edge; PixelLab drew no chair). Moving or E stands you up; the Sit emote takes the nearest seat or the floor.
93. **Multiplayer = a new Durable Object, `MemoryWalkRoom`** (migration v3; `workers/memory-walk.js`), one per spot, hibernating WebSockets. Not ArcadeRoom (public vs the password). A bearer-checked `POST /spots/:id/walk` mints an HMAC ticket (120 s, the file-signing key) for `GET /walk/ws?t=…` (401 without, 403 bad, 426 not an upgrade). It relays state / emote / chat and stores nothing: the sockets and their attachments are the presence (the last position goes into the attachment at most once a second, for hibernation). **You're announced with your first position, never before** (a join with the DO's placeholder drew newcomers in the room's corner for ~200 ms, then they glided through the wall); until then you count for the spot page's presence but nobody draws you, and a socket that never placed anyone leaves no "left" line. Pings get a WebSocket auto-response (the room isn't woken) and an alarm every 60 s closes sockets quiet for 75 s, so a phone that vanished mid-walk doesn't stay "in this room". Limits: 24 states/s per socket, 6 chats per 10 s, 80 characters, control characters stripped; a move faster than 7 m/s (over at most 1 s since the last state, so standing still earns no long jump) + 1.2 m slack is clamped and the sender gets `correct`. A ticket can be reused within its 120 s, and the first position after a (re)connect is taken as given (anywhere within 500 m): both accepted for two people behind one password. *Found on the way:* the page sent its position before the room had loaded (0, 0, 0), so the server clamped the real spawn as a teleport and put the walker inside furniture; the game now sends nothing until it's ready, and a correction snaps to the nearest walkable cell.
94. **The client** (`walk/net.js`) takes a new ticket for every connection, retries 1 → 15 s, and offline keeps you walking alone with one line. Others are drawn 100 ms behind, interpolated, snapping on a jump over 2 m; ~12 Hz while moving, nothing while still.

## Next level: whole buildings + the "Recall" look (2026-11-21, unattended)

Brief: `Documents/temp/prompt-dumping/memory-rooms-next-level.md`; spec: the vault's `2026-11-21-memory-rooms-next-level-plan`. Built unattended; each phase committed on `main` when green.

### Phase 0 · contracts

97. **scene.json v2 lives in the same schema file** (`version: 1 | 2`). A v1 scene may not use any v2 key (`shellV1Rules`: no `outline`, `building`, `room`, ceiling `shape`, opening `edge`), so v1 means exactly what it meant. Every existing scene (2 examples + 6 work folders) still validates in JS and Python, and check-scene prints byte-identical output for all of them (a flat box goes down the original code path). *Change:* `src/memory-rooms/scene/scene.schema.json`.
98. **A polygon outline is the walls' inner faces and its bounding box must start at [0, 0]** (an error that says what to subtract), so every consumer that thinks in `[0..width] × [0..depth]` can work on the bounding box once it reads the normalised shell (`sceneBounds` does from Phase 0; the viewer, hero view, walk and AR move over in Phase 3: until then don't push a v2 scene to a deployed Worker). Either winding is accepted; `resolveShell` normalises it. Edges are named by index (`edge: i`, GLB `wall__e<i>`). *Change:* `shellChecks` in `scene/validate.js` + `scene_io._shell_checks`.
99. **One ceiling function, `ceilingAt(shell, x, z)`, over the outline's bounding box**: gable (ridge `axis` + `ridgeAt`, per-side `eaves` because the Lunch Room's are 3.46 / 3.40 m), pyramid (ray scale from `apex`, so a star-shaped room works, not just convex), skillion (`low` side). Wall tops follow it, so a gable's end walls rise to the ridge with no bespoke trimming. *Change:* `scene/shell.js` (+ Python `scene_io.ceiling_at`, kept equal by check-contracts).
100. **The room frame of a building's room = `room.origin` when set, else its wall-CENTRELINE bounding box**, not its inner faces. Thickening or thinning a wall doesn't move the furniture (the floor starts at half a thickness), and the fixed `origin` (which `sketchToBuilding` sets to every sketched room's corner) means re-tracing the walls can't move it either. *Change:* `roomFrame` in `building/geometry.js` + `building_io.room_frame`.
101. **building.json ids are `[a-z0-9-]`, no underscores**, so `__` splits GLB names (`wall__g-n1__window0`) unambiguously. Wall ids are unique across the building (openings name a wall without its level); node ids per level.
102. **Wall-graph rules are errors, not warnings**: two walls on one node pair, collinear overlaps, crossings without a node, a node on another wall's middle, exterior walls that don't close into loops. "Shared walls exist once" only holds on a clean graph; the sketch converter and the tracing step both produce one, and a hand edit that breaks it says exactly which wall to split.
103. **Stairs are straight flights in v1** (`start` = the middle of the bottom step's front edge, `dir`, `width`, `length`, `steps`), and the upper floor's hole over a flight is automatic: no "void" room to keep in sync. L and U stairs can be two flights and a landing room later. *Change:* `stair` in `building.schema.json`.
104. **The roof follows the exterior outline split into rectangles, or explicit `parts`** (each with its own type and, for a single-storey wing, its own `level`). The parts merge where they meet (Phase 4), which gives valleys on an L-shaped house without a straight-skeleton solver. The example house uses a hip main roof + a skillion garage.
105. **GLB walls: v1 keeps `wall_<side>`; v2 scenes and buildings use `wall__<id>`** with the outward normal in glTF extras (`mrWall.normal`; buildings: the left normal looking a → b plus the rooms on each side). The viewer hides walls by normal; the legacy names map to normals. `export_extras` goes on in the bake (Phase 3).
106. **Building media**: level models are `level-<levelId>` (stable when a level is added, unlike an index); `exterior.glb` = roof + site only, because the facades are the outer faces of the level GLBs' walls, lit in the same per-level solve (sky + sun included). Each room spot also gets its own `room.glb`, a slice of its level's bake moved into its room frame, so the spot page, walk and AR need no building code. *Change:* CONTRACTS.md 6.4.
107. **The phone's sketch is its own small JSON on the building row (`sketch`), separate from building.json (`plan`)**: levels + rooms, each optionally drawn (`rect`) and/or marked on a floor-plan photo (`mark`). It is the room checklist. `sketchToBuilding` turns the drawn rooms into a first, valid building.json (split walls, exterior = a room on one side only) and room ids carry over, so spots captured on the trip land in the right rooms after tracing. No Python mirror: only the phone and the Worker write it.
108. **Spots gain `buildingId` + `roomId` without a foreign key.** A spot must never fail to save because its building's row isn't there yet (the outbox sends the building first, but a stuck building must not strand its rooms). `frameGroup` stays as the legacy way to assemble a house.
109. **`tools/memory-rooms/check-contracts.mjs`** runs the JS and Python sides over every example and work scene, 33 broken mutations (both must fail at the same paths, including the expected one) and the geometry (normalised shells, ceilings on a grid, room frames, exterior loops, stairs, lng/lat) to 1e-6, plus the sketch converter. 178 checks.
110. **Two independent reviews of the contracts (2026-11-21), and what they changed.** Nothing broke v1 (both diffed the old and new validators over every scene, 18,000 fuzzed copies and 4,000 mutated v1 scenes). Fixed: a strip overlap between two rooms (every corner on the other's sides) passed; near-parallel walls of two thicknesses threw an inset corner 20 m away (now treated as parallel past 10× the offset); a room side that skipped a junction node silently became an open side (now an error); an object straddling an L's inside corner passed check-scene; a broken building crashed check-scene; push couldn't find a room's building.json; sketches with corner-only contact or 1 cm slivers made invalid buildings (now refused). Python mirrored `round()` (banker's) where JS uses `Math.round`, `re.search`'s `$` accepted a trailing newline, and `true == 1` let `version: true` through: all fixed. Every case is now a check-contracts test (226 checks).
111. **Openings must clear the walls they meet** (offset ≥ half the thickest other wall at node a, and the same at b), so no door starts inside the wall it tees into. *Why:* the room's inner face starts there; a door at offset 0 cut 12.5 cm into the exterior wall.
112. **Levels must stack**: a floor's structure (`elevation − slab`) may not cut into the level below. Exterior walls run up to the next floor, so a gap between the lower ceiling and the upper slab is just the floor void, never a hole in the facade.
113. **`rooms[].origin` pins a room frame**; `sketchToBuilding` sets it to each sketched room's corner. *Why:* the room frame used to follow the wall-centreline bounding box, so re-tracing a wall on a room's north or west side would have shifted every object, camera and pin in its scene.json.
