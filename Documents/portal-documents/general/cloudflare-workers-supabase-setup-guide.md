# Reproducing This Repo's Stack: React Router 7 on Cloudflare Workers + Supabase

> **Audience:** another Claude Code instance standing up a *new* project that mirrors this repo's
> architecture. You cannot see the source repo — everything you need to copy is below.
>
> **What this stack is:** A server-side-rendered **React Router v7** app that runs as a **single
> Cloudflare Worker** (not Pages, not a separate Node server). The same Worker serves HTTP,
> processes Cloudflare Queues, and runs Cron triggers. **Supabase** is the primary database,
> accessed via `@supabase/supabase-js` created per-request. Secrets live in `.dev.vars` locally
> and as Wrangler secrets in production; non-secret config lives in `wrangler.jsonc`.
>
> **Priority order of this guide:** (1) Supabase, (2) Cloudflare Workers vs Pages, (3) env vars / `.dev.vars`.

---

## 0. TL;DR decisions baked into this stack

| Concern | This repo's choice |
|---|---|
| Hosting | **Cloudflare Workers** (`main: ./workers/app.ts`, `wrangler deploy`) — *not* Pages |
| Framework | React Router v7 in **framework/SSR mode** (`ssr: true`) |
| Bundler | Vite 6 with `@cloudflare/vite-plugin` |
| DB | Supabase (Postgres) via `@supabase/supabase-js`, client created per call/request |
| Env access in code | Both `process.env.X` (works because of `nodejs_compat`) **and** `context.cloudflare.env.X` (React Router loader/action context) |
| Secrets locally | `.dev.vars` (gitignored) |
| Secrets in prod | `wrangler secret put NAME` |
| Non-secret config | `vars` block in `wrangler.jsonc` (committed) |
| Types | `worker-configuration.d.ts` generated by `wrangler types` |

## 1. Supabase Integration (HIGHEST PRIORITY)

### 1.1 How it's wired

- Dependency: `@supabase/supabase-js` (this repo pins `^2.49.4`).
- **There is no shared/singleton client.** A fresh client is created at each call site with
  `createClient(url, key)`. This is deliberate for Workers — a Worker isolate handles many
  requests, and you should not leak a stateful client across requests. Create it inside the
  loader/action/handler that needs it.
- Two credentials are used:
  - `SUPABASE_URL` — the project URL, e.g. `https://<your-project-ref>.supabase.co`. **Not secret** → lives in `wrangler.jsonc` `vars` (committed).
  - `SUPABASE_KEY` — the API key used by the server (service-role or anon depending on your RLS posture). **Secret** → lives in `.dev.vars` locally and as a Wrangler secret in prod.
  - `SUPABASE_PASSWORD` — the Postgres DB password. Held as a secret but **not used by the JS client**; keep it only if you need direct Postgres/migration access.

### 1.2 The two access patterns (copy these exactly)

**Pattern A — `process.env` (most common in this repo; used in plain `.js` libs and crons/queues):**

```js
import { createClient } from "@supabase/supabase-js";

const supabase_url = process.env.SUPABASE_URL;
const supabase_key = process.env.SUPABASE_KEY;
if (!supabase_url || !supabase_key) {
  throw new Error("Supabase URL or Key is not defined");
}
const supabase = createClient(supabase_url, supabase_key);
```

`process.env` works inside the Worker **only because** `nodejs_compat` is enabled and the
compatibility date is recent — Wrangler then auto-populates `process.env` from the Worker's
`vars` + secrets. (See §2.4.)

**Pattern B — React Router loader/action `context` (preferred inside route loaders/actions):**

```ts
export async function loader({ request, context }: Route.LoaderArgs) {
  const supabaseUrl = context.cloudflare.env.SUPABASE_URL;
  const supabaseKey = context.cloudflare.env.SUPABASE_KEY;
  const supabase = createClient(supabaseUrl, supabaseKey);
  const { data, error } = await supabase.from("user").select("*").eq("id", id);
  // ...
}
```

`context.cloudflare.env` is the canonical Worker `env` object — it is the most reliable source in
request scope. (See §2.3 for how the context is typed.)

**Pattern C — robust helper that tries both (recommended to copy verbatim):**

```js
import { createClient } from "@supabase/supabase-js";

export function get_supabase_client(context) {
  const supabase_url = context?.cloudflare?.env?.SUPABASE_URL || process.env.SUPABASE_URL;
  const supabase_key = context?.cloudflare?.env?.SUPABASE_KEY || process.env.SUPABASE_KEY;
  if (!supabase_url || !supabase_key) {
    throw new Error("Supabase URL or key is not set in environment variables.");
  }
  return createClient(supabase_url, supabase_key);
}
```

Use this helper everywhere so code works in both request scope (where `context` exists) and
background scope (queue/cron handlers, where you pass `env` through and rely on `process.env`).

> **Known footgun carried from this repo:** never chain `.or()` / `.and()` onto a Supabase
> `.update()` / `.delete()` — PostgREST throws a 42703 ("column does not exist") even when the
> column exists. Use plain `.eq()` / `.is()` compare-and-swap filters on mutations instead.

### 1.3 Reproduce Supabase in a fresh project — steps

1. Install the client:
   ```bash
   npm install @supabase/supabase-js
   ```
2. Put the **URL** in `wrangler.jsonc` under `vars` (committed, non-secret):
   ```jsonc
   "vars": {
     "SUPABASE_URL": "https://<your-project-ref>.supabase.co"
   }
   ```
3. Put the **key** in `.dev.vars` for local dev (gitignored):
   ```
   SUPABASE_KEY=<your-supabase-api-key>
   ```
4. Push the key to production as a secret:
   ```bash
   npx wrangler secret put SUPABASE_KEY
   ```
5. Regenerate types so `process.env.SUPABASE_*` and `env.SUPABASE_*` are typed:
   ```bash
   npm run cf-typegen   # = wrangler types
   ```
6. Create the client per call using Pattern C above.

## 2. Cloudflare Deployment — this repo uses **Workers** (not Pages)

### 2.1 How we know it's Workers

- There is a **`wrangler.jsonc`** with a top-level `main` entrypoint pointing at a Worker module:
  `"main": "./workers/app.ts"`. (Pages projects do not declare `main` like this; they use a
  `pages_build_output_dir` / `functions/` directory instead.)
- `package.json` deploys with **`wrangler deploy`**, the Workers deploy command (Pages would use
  `wrangler pages deploy ./build/...`).
- The Worker exports `fetch`, `queue`, and `scheduled` handlers — Queues + Cron triggers are
  Workers-only features and are configured inside `wrangler.jsonc`.
- The build uses `@cloudflare/vite-plugin`, which builds a Worker bundle for the SSR environment.

### 2.2 The Worker entry point (`workers/app.ts`)

This single module is the whole server. Copy this shape:

```ts
import { createRequestHandler } from "react-router";
// ...import your queue/cron handlers...

declare module "react-router" {
  export interface AppLoadContext {
    cloudflare: {
      env: Env;
      ctx: ExecutionContext;
    };
  }
}

const requestHandler = createRequestHandler(
  () => import("virtual:react-router/server-build"),
  import.meta.env.MODE
);

export default {
  // 1) HTTP — React Router SSR. This is what makes context.cloudflare.env work in loaders/actions.
  async fetch(request, env, ctx) {
    return requestHandler(request, { cloudflare: { env, ctx } });
  },

  // 2) Cloudflare Queues — one consumer fn, branch on batch.queue
  async queue(batch: MessageBatch<any>, env: Env, ctx: ExecutionContext) {
    if (batch.queue === "my-queue") {
      for (const msg of batch.messages) {
        try { await handle(msg.body, env, ctx); msg.ack(); }
        catch (err) { console.error(err); msg.retry(); }
      }
    }
  },

  // 3) Cron triggers — fan out from a single scheduled handler
  async scheduled(event, env, ctx) {
    cron_handler(event, env, ctx);
  },
} satisfies ExportedHandler<Env>;
```

Key point: the `fetch` handler injects `{ cloudflare: { env, ctx } }` as the React Router load
context. That is the wiring that makes `context.cloudflare.env.SUPABASE_URL` available in every
loader/action. If your new project is HTTP-only, you can omit `queue` and `scheduled`.

### 2.3 `wrangler.jsonc` — minimal template for a new project

The real file in this repo is large (KV, R2, Durable Objects, Queues, Cron, Images, email).
Strip it down to what a new project needs and add bindings back as required:

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "<your-worker-name>",
  "compatibility_date": "2026-01-31",
  "compatibility_flags": ["nodejs_compat"],
  "account_id": "<your-cloudflare-account-id>",
  "main": "./workers/app.ts",

  // Custom domains (optional). Each becomes a route on your Worker.
  "routes": [
    { "pattern": "app.example.com", "custom_domain": true }
  ],

  // Non-secret, committed config. process.env + env are populated from here.
  "vars": {
    "ENVIRONMENT": "development",
    "SUPABASE_URL": "https://<your-project-ref>.supabase.co"
  },

  // --- everything below is OPTIONAL; include only what you use ---

  "kv_namespaces": [
    { "binding": "MY_KV", "id": "<kv-namespace-id>" }
  ],
  "r2_buckets": [
    { "binding": "MY_BUCKET", "bucket_name": "<r2-bucket-name>" }
  ],
  "queues": {
    "producers": [{ "binding": "MY_QUEUE", "queue": "my-queue" }],
    "consumers": [{ "queue": "my-queue", "max_batch_size": 1, "max_retries": 3 }]
  },
  "triggers": {
    "crons": ["*/10 * * * *"]
  },
  "observability": { "enabled": true }
}
```

Notes carried from the real config:
- `compatibility_flags: ["nodejs_compat"]` is **required** for `process.env` + many npm libs.
- Bindings declared here appear on the `env` object passed to `fetch`/`queue`/`scheduled` and on
  `context.cloudflare.env` in loaders. Access R2/KV/Queues as `context.cloudflare.env.MY_BUCKET`.
- Some bindings in this repo use `"remote": true` (use the real remote resource during local
  `dev` instead of a local simulation) — handy for KV/R2/email you can't simulate locally.

### 2.4 Why `process.env` works (the `nodejs_compat` mechanism)

With `nodejs_compat` enabled and a recent `compatibility_date`, the Workers runtime + Wrangler
expose your `vars` and secrets on `process.env` automatically. `wrangler types` even generates a
`NodeJS.ProcessEnv` interface (in `worker-configuration.d.ts`) listing every var/secret key, so
`process.env.SUPABASE_KEY` is type-checked. That is why this repo can use `process.env.X` (≈660
sites) freely alongside `context.cloudflare.env.X` (≈440 sites). Without `nodejs_compat`,
`process.env` would be empty and only `env` / `context.cloudflare.env` would work.

### 2.5 Build & deploy commands (`package.json` scripts)

```json
{
  "scripts": {
    "dev": "react-router dev",
    "build": "react-router build",
    "preview": "npm run build && vite preview",
    "deploy": "npm run build && wrangler deploy",
    "cf-typegen": "wrangler types",
    "typecheck": "npm run cf-typegen && react-router typegen && tsc -b"
  }
}
```

- **Local dev:** `npm run dev` → Vite dev server on `http://localhost:5173`, with the Worker
  runtime via `@cloudflare/vite-plugin`. `.dev.vars` is loaded automatically.
- **Deploy to prod:** `npm run deploy` (builds then `wrangler deploy`).
- **Preview release (no traffic):** `npx wrangler versions upload`, then promote with
  `npx wrangler versions deploy`.

### 2.6 Mapping to your new project: Pages vs Workers

Your new project is currently on **Cloudflare Pages** but may move to **Workers**. Here's how this
repo's approach maps, and what differs:

| Aspect | This repo (Workers) | If your new project stays on **Pages** | Moving Pages → **Workers** |
|---|---|---|---|
| Config file | `wrangler.jsonc` with `main` | `wrangler.toml`/dashboard with `pages_build_output_dir`; server code in `functions/` | Add `main` + entry module; drop Pages-specific config |
| Deploy cmd | `wrangler deploy` | `wrangler pages deploy <outDir>` (or Git auto-deploy) | Switch script to `wrangler deploy` |
| React Router preset | default Workers/Vite plugin | `@react-router/cloudflare` Pages preset / `functions/[[path]].ts` | Use `workers/app.ts` entry like §2.2 |
| Env/secrets (local) | `.dev.vars` | `.dev.vars` (Pages supports it too) | unchanged |
| Env/secrets (prod) | `wrangler secret put` | Pages dashboard → Settings → Env vars, or `wrangler pages secret put` | re-add as `wrangler secret put` |
| Non-secret config | `vars` in `wrangler.jsonc` | `vars` in Pages config / dashboard | move into `wrangler.jsonc` `vars` |
| Queues / Cron / Durable Objects | ✅ native | ❌ **not supported on Pages** — needs a separate Worker | ✅ becomes available |
| `context.cloudflare.env` | from the `fetch` handler (§2.2) | from the Pages `functions` adapter context | unchanged shape: `context.cloudflare.env` |

**Bottom line for the migration decision:** if the new project needs **Queues, Cron triggers,
Durable Objects, or a single deploy unit that owns background processing** (as this repo does),
choose **Workers** and copy §2.2–§2.5. If it's a straightforward SSR site with no background work,
Pages is fine and the Supabase + `.dev.vars` parts of this guide still apply unchanged — only the
deploy command and the absence of `main`/queues/crons differ.

> **Repo doc note:** this repo's `README.md` mentions a second `wrangler-consumer.jsonc` →
> `workers/queue-consumer.ts` split (a separate Worker just for queue consumers). **Those files do
> not currently exist** in the repo; queue consumers are defined inline in `wrangler.jsonc` and
> handled by the `queue()` export in `workers/app.ts`. Treat the split-consumer setup as an
> optional advanced pattern, not the current state. Don't chase the missing file.

## 3. Environment Variables & `.dev.vars`

### 3.1 The three buckets of config (this is the mental model)

1. **Non-secret runtime config** → `vars` block in `wrangler.jsonc` (committed). Examples here:
   `ENVIRONMENT`, `SUPABASE_URL`, API base URLs, account IDs, shop handles, batch sizes.
2. **Secret runtime config** → `.dev.vars` locally (gitignored), `wrangler secret put` in prod.
   Examples here: `SUPABASE_KEY`, `SESSION_SECRET`, all API tokens/passwords/client secrets.
3. **Shell-tooling config** (NOT the Worker runtime) → `.env` / `.env.sample` / `.envrc`, read by
   helper shell scripts only. Example: `PINGGY_TOKEN` consumed by `getEnv.sh` + `host.sh` to open
   a tunnel. Do not confuse these with Worker env — the Worker never reads `.env`.

### 3.2 `.dev.vars` — how it's used locally

- It's a flat `KEY=value` file at the repo root (dotenv-style, no `export`, no quotes needed).
- `wrangler` / `@cloudflare/vite-plugin` load it automatically during `npm run dev` and inject
  every key into the Worker `env` (and therefore `process.env` and `context.cloudflare.env`).
- It is **gitignored** (see §3.5) and must never be committed.

### 3.3 How the same vars reach production (Cloudflare)

- **Secrets:** one-time per key, run `npx wrangler secret put SUPABASE_KEY` (prompts for the
  value; stored encrypted on Cloudflare). Repeat for each secret in `.dev.vars`. For Pages it'd be
  `wrangler pages secret put` or the dashboard.
- **Non-secrets:** edit the `vars` block in `wrangler.jsonc` and `wrangler deploy` — they ship with
  the deploy, no separate step.
- You do **not** upload `.dev.vars` anywhere; it's purely local.

### 3.4 How vars are typed & accessed in code

- `npm run cf-typegen` (`wrangler types`) writes **`worker-configuration.d.ts`**, which declares:
  - `interface Env` — every binding (KV/R2/Queues/etc.) + every var/secret key, used as
    `ExportedHandler<Env>` and on `context.cloudflare.env`.
  - `namespace NodeJS { interface ProcessEnv ... }` — every var/secret key, so `process.env.X` is typed.
- Re-run `cf-typegen` whenever you add a var/secret or binding, then commit the regenerated
  `worker-configuration.d.ts`.
- Access in code via Pattern A/B/C from §1.2.

The critical lines for secrets: **`.dev.vars*`** and **`.env`**. (`.env.sample` is *not* ignored —

### 3.6 `.dev.vars` template for the new project

Start minimal and add keys as you integrate each service. Replace every placeholder; do **not**
commit real values.

```bash
# .dev.vars  — local Cloudflare Worker secrets (GITIGNORED, never commit)

# --- Core / app ---
SESSION_SECRET=<random-long-string>     # if you sign session cookies/JWTs
ACCESS_KEY=<internal-api-access-key>     # optional shared-secret gate, if used

# --- Supabase (URL goes in wrangler.jsonc vars, key is the secret) ---
SUPABASE_KEY=<supabase-api-key>
SUPABASE_PASSWORD=<supabase-db-password> # only if you need direct Postgres/migrations

# --- Add per-integration secrets below as you wire them up, e.g.: ---
# OPENAI_API_KEY=<...>
# SHOPIFY_*_ACCESS_TOKEN=<...>
# XERO_CLIENT_ID / XERO_CLIENT_SECRET=<...>
```

> The real repo's `.dev.vars` holds ~110 keys spanning Supabase, Shopify (multiple stores), Xero,
> NetSuite, Australia Post, AWS, Azure, Google, Brevo, Hoya, ShipBob, Starshipit, Dropbox,
> Instagram, Missive, Mapbox, SignatureAPI, eWAY, PDF service, and more. **Do not copy those** —
> add only the secrets your new project actually uses. Names only are reproduced here so you know
> the convention (`<SERVICE>_<ROLE>` / `<SERVICE>_<ENV>_<ROLE>`).

### 3.7 `.env.sample` (committed template for shell tooling, separate from `.dev.vars`)

If you keep the shell-tunnel/helper-script pattern, commit a sanitized sample like this repo's:

```
PINGGY_TOKEN=*********
OPENAI_API_KEY=*********
# ...other shell-script-consumed keys, values masked with *********
```

Read by `getEnv.sh` (`grep`s a key out of `.env`) and `host.sh` (opens an SSH tunnel). Most new
projects can skip this entirely — it's a local dev-tunnel convenience, not part of the deployed app.

## 4. Full bootstrap checklist for the new project

```bash
# 1. Scaffold a React Router v7 + Cloudflare Workers app (or copy the configs below into one)
npx create-react-router@latest --template remix-run/react-router-templates/cloudflare my-app
cd my-app

# 2. Core deps used by this stack
npm install @supabase/supabase-js
npm install -D wrangler @cloudflare/vite-plugin @cloudflare/workers-types \
               @react-router/dev @tailwindcss/vite tailwindcss vite vite-tsconfig-paths typescript

# 3. Create the files (see sections above for contents):
#    - wrangler.jsonc          (§2.3)   main: ./workers/app.ts, compatibility_flags: [nodejs_compat], vars.SUPABASE_URL
#    - workers/app.ts          (§2.2)   fetch handler injecting { cloudflare: { env, ctx } }
#    - vite.config.ts          (§4.1)
#    - react-router.config.ts  (§4.2)   ssr: true
#    - .dev.vars               (§3.6)   SUPABASE_KEY, etc.  (gitignored)
#    - .gitignore              (§3.5)   include .dev.vars* and .env

# 4. Generate types and verify
npm run cf-typegen          # writes worker-configuration.d.ts (commit it)
npm run typecheck

# 5. Run locally (loads .dev.vars automatically)
npm run dev                 # http://localhost:5173

# 6. Push production secrets, then deploy
npx wrangler secret put SUPABASE_KEY
npm run deploy
```

## 5. Gotchas to carry over

- **Always enable `nodejs_compat`** or `process.env.*` (and many npm libs) silently break.
- **Create Supabase clients per request/handler**, never as a module-level singleton shared across
  requests in a Worker isolate.
- **Re-run `wrangler types` after any env/binding change** and commit `worker-configuration.d.ts`.
- **`.dev.vars` is local-only**; production secrets are a separate `wrangler secret put` step.
- **Pages can't do Queues/Cron/Durable Objects** — if the new project needs those, it must be a
  Worker (or add a companion Worker).
- **Supabase mutation filter bug:** don't chain `.or()`/`.and()` onto `.update()`/`.delete()`.
- **`AGENTS.md` rule from this repo:** always ask before manipulating Supabase tables, and never
  commit secrets / log tokens.
